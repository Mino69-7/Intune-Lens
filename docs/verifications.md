### Points relevés pendant la vérification

- **V22** : la page Learn des assignations de `deviceManagementScripts` est introuvable sous les URL que j'ai essayées. Le motif `{id}/assignments` est supposé par analogie avec les autres types. **À confirmer en M6** : une erreur 400/404 apparaîtrait dans le journal comme « Assignations illisibles … (HTTP xxx) ».
- **V23** : la page Learn d'Autopilot est introuvable sous les URL que j'ai essayées. Le scope `DeviceManagementServiceConfig.Read.All` reste une **hypothèse**, cohérente avec la page Inscription / ESP. Sans conséquence : le type n'est jamais lu sans activation explicite et permission présente dans le jeton.
- **Contenu des scripts** : les listes de `deviceManagementScripts` et `deviceHealthScripts` renvoient le **contenu des scripts** (`scriptContent`, `detectionScriptContent`, `remediationScriptContent`) quand on ne précise pas `$select`. L'outil demande toujours un `$select` minimal, ce que le test vérifie pour chaque type. Le contenu des scripts n'est donc jamais téléchargé ni mis en cache.
- **Nouvelles cibles** : `scopeTagGroupAssignmentTarget` (V18) et `configurationManagerCollectionAssignmentTarget` apparaissent dans les exemples. Les cibles non prises en charge sont **conservées** et affichées sur l'écran de l'élément (« Cible non prise en charge (…) ») au lieu d'être ignorées.
- **Conséquence pour la validation du groupe de référence (spec 9.5)** : si les 26 éléments de la liste de référence incluent des **remédiations**, l'outil n'en affichera aucune par défaut. Pour les inclure, il faut deux conditions :
  1. le jeton contient déjà `DeviceManagementScripts.Read.All` ; l'outil le signale alors dans le menu de la pastille (« activable avec -EnableOptionalTypes deviceHealthScripts ») ;
  2. vous relancez avec `-EnableOptionalTypes deviceHealthScripts`.
  Aucune permission n'est jamais demandée par l'outil.
